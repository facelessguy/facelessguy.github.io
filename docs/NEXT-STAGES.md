# Следующие стадии платформы

По принятому плану каждый инфраструктурный этап начинается после готовности предыдущего и появления функции, которой он нужен. Первый выпуск сейчас ожидает реальные кейсы, демо и контакты. Поэтому FastAPI, база, сбор событий и VPS пока не включены; Docker и серверные зависимости не добавлены в статический сайт.

## Стадия 2 — измерение использования

Условие начала: сайт с реальными материалами опубликован, сформулирован вопрос к аналитике. Например: какие кейсы приводят к контактам и какие демо проходят до конца.

Реализовать отдельный сервис FastAPI + SQLAlchemy + PostgreSQL с миграциями Alembic:

- `GET /health`: проверка приложения и доступности базы, без подробностей инфраструктуры в ответе.
- `POST /api/v1/events`: `event_id` (UUID), `type` из разрешённого списка и `target_id` (существующий slug проекта/демо или фиксированный идентификатор контакта). Время задаёт сервер, остальные поля запрещены.
- Типы: `project_view`, `demo_start`, `demo_complete`, `github_click`, `contact_click`. Просмотр страницы не называть прочтением кейса.
- Уникальный индекс `event_id`, идемпотентная повторная отправка, проверка допустимых сочетаний типа события и цели.
- Ограничение частоты запросов и размера тела, проверка Origin по списку разрешённых источников. Origin не является доказательством подлинности события; отчёты трактуются как приблизительные.
- Клиент отправляет события без блокировки переходов, короткий timeout, ограниченные повторы с тем же идентификатором. При отказе API сайт и демо продолжают работать.
- Не отправлять IP, email, свободный текст, параметры URL и содержимое полей в модель событий. Проверить также журналы reverse proxy и сервера; определить срок хранения до запуска сбора.

`demo_start` означает клик по запуску. `demo_complete` подключать отдельно к каждому реальному демо: требуется сигнал завершения сценария, а не таймер или закрытие вкладки. Для демонстраций без такого сигнала завершения не собирать. При обмене через postMessage проверять origin, источник окна и идентификатор демо. Клиентский сигнал не считать доверенной LMS-аттестацией.

Закрытая CLI-выгрузка строит отчёт за период по кейсам, запускам, подтверждённым завершениям, переходам к коду и контактам. Персональных профилей и административной панели нет. Без идентификатора сессии не рассчитывать пользовательскую воронку или уникальных посетителей: показывать счётчики событий, не заявляя точную конверсию человека.

Проверки: валидный запрос, неизвестная цель, дополнительные поля, неверный Origin, превышение лимита, повторный UUID, потеря базы, отключённый API, неполный/полный проход демо, миграция пустой базы.

## Стадия 3 — VPS

Условие начала: серверная функция проверена, выбран оплачиваемый сервер и домен. Окончательная конфигурация зависит от конкретных приложений и размера демо.

- Compose запускает Caddy, FastAPI и PostgreSQL. Снаружи доступны только HTTP/HTTPS; база не публикует порт. Caddy раздаёт статическую сборку и проксирует API.
- Поддомены: основной сайт, `demo`, `apps`, `api`. Самостоятельные приложения разворачиваются отдельными сервисами и репозиториями.
- Секреты хранятся вне Git, постоянные данные — в именованных volumes. Выполняются healthchecks; порядок запуска не заменяет ожидание готовности базы.
- Ежедневный `pg_dump` загружается в отдельное внешнее хранилище; перед переходом на VPS выполнить восстановление в чистую тестовую базу. Настроить уведомление о сбое резервирования.
- Проверить HTTPS, обновление сертификатов, миграции, доступность доменов и поведение при остановке API. Сайт должен продолжать раздаваться.
- При переносе демо сохранить старые пути через 301. Сначала развернуть и проверить VPS, затем переключать DNS. Cloudflare-публикацию сохранить для отката; учесть TTL DNS и совместимость версии схемы базы.

Render Free можно использовать для проверки API, но не как гарантию моментального ответа: сервис засыпает после 15 минут бездействия. Тарифы, лимиты и доступность выбранных провайдеров проверяются непосредственно перед развёртыванием.
